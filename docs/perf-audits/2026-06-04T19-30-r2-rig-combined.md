## Hardware-unfalsifiable caveat (read first)

The dynamic lane CANNOT run here: measuring serial-RTS or CM108-HID latency needs a
real rig + `/dev/ttyUSB*` / `/dev/hidraw*` device. All findings below rest on
structure/complexity arguments only. The allocation fallback the rust pack offers is
**weak and inapplicable** — PTT control has essentially no allocation on its path
(`Cm108Report` is a stack `[u8; 5]`; the RTS path builds a stack `c_int`). This is
timing/latency code, and the timing dimension is exactly what cannot be measured
without hardware. Treat every confidence below as bounded by that.

## What was examined

- **Device-handle lifetime** (data-access): does either backend re-open the device
  per toggle, or hold it open? — `LinuxTty` (`linux.rs:25-78`) and `HidrawWriter`
  (`hidraw.rs:31-62`) both OWN the fd for the writer's lifetime; `RtsPtt`/`Cm108Ptt`
  wrap the writer once. assert/release reuse the same fd. **No per-toggle reopen.** Good.
- **Syscall pattern on the latency path** (data-access): RTS uses one `libc::ioctl`
  per op (`linux.rs:144`); CM108 uses one `write(2)` of 5 bytes, no flush
  (`hidraw.rs:65-81`, deliberate — comment 77-80). Single syscall per toggle; no
  buffering needed (and `BufWriter` would be wrong here — these are control ops that
  must hit the wire immediately).
- **Watchdog loop** (concurrency): `run_watchdog` (`watchdog.rs:64-95`) is a
  **sleep-poll, not a busy-wait** — `std::thread::sleep(poll_interval.min(remaining))`
  at line 90. No lock is held anywhere in the loop; flags are lock-free `AtomicBool`
  with `Acquire`/`Release` ordering (lines 79-82). No lock-across-I/O.
- **Lock-across-blocking-I/O** (concurrency): none. `Ptt` is `&mut self`, single-owner;
  `ptt.rs` docs explicitly forbid cross-thread sharing without external sync. No
  `Mutex`/`RwLock` in scope at all.
- **Thread lifecycle** (concurrency): the only threads are in `#[cfg(test)]` and are
  detached (`let _t = ...`, `watchdog.rs:166,199`) — test-only, out of scope for prod.

## Findings

### [1] Watchdog poll granularity bounds key-down latency (sleep-poll) (concurrency)

Location: `tux-rig-rts/src/watchdog.rs:78-91`

Problem: the exit-condition latency is bounded below by `poll_interval`. After
`signal`/`stdin_eof` is set, the loop only notices on the next wake from
`thread::sleep(poll_interval.min(remaining))`. With a coarse `poll_interval` the
worst-case delay between "parent died / SIGTERM" and "PTT released" is ~one
`poll_interval`. This is the standard sleep-poll latency/CPU tradeoff, not a defect —
a blocking primitive (e.g. blocking read on stdin for EOF, or a `Condvar`) would give
near-zero release latency without the polling wake-ups, but adds complexity the
infrequent-toggle workload doesn't obviously justify.

Impact: LOW. The watchdog is the SIGKILL backstop; release latency here is
operator-visible only as extra dead-air after a crash, not on the normal TX path.
Caller picks `poll_interval`; the binary (out of scope) sets it.

Confidence: MEDIUM (structure-clear; the actual `poll_interval` value lives in the
out-of-scope binary, so the realized latency is unmeasurable here).

Effort: M (swap timer-poll for a blocking/Condvar wait — only if a future profile
shows post-crash dead-air matters).

Verification (hardware lane, cannot run here): on a real rig, assert PTT via the
watchdog, kill the parent, scope the RTS line; measure the parent-death → line-low
interval across `poll_interval` values; confirm it tracks `poll_interval`.

## Suspected Bugs

None. (Both Drop impls release on `Asserted` only and are idempotent vs. explicit
release; the watchdog always reaches `ptt.release()` on every exit path and falls
back to Drop if release errors — `watchdog.rs:93`. No path observed where the
watchdog fails to attempt key-down.)
