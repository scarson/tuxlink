# Perf audit R5 — AX.25 data access & I/O / link concurrency

Agent: glade-knoll-shoal. Dimension: data access & I/O / concurrency-of-the-link.
Scope: `src-tauri/src/winlink/ax25/{datalink,frame,kiss,link,rfcomm,mod}.rs`.
Lens prior: profile-packs/rust.md (data-access + concurrency lanes).
Load context: 1200/9600-baud half-duplex link (LOW rate). Impact ceiling LOW.

## What was examined

- **Read path:** `recv_frame` (datalink.rs:164) reads into a `[0u8; 512]` chunk, feeds
  `KissDecoder::push` — chunked, NOT byte-at-a-time. Transports (`RfcommSocket::read`
  rfcomm.rs:222, `TcpStream`, serialport) all do one `read()` syscall per `recv_frame`
  poll into that 512-byte buffer.
- **Write path:** `send_frame` (datalink.rs:154) does a single `write_all` of one fully
  built KISS frame. `push_kiss_params` (datalink.rs:765) = 3 `write_all`s, once per connect.
- **Locks across I/O:** The real transports hold NO `Mutex`/`RwLock` across `read`/`write`.
  The `Arc<Mutex<…>>` in link.rs:217 and rfcomm decompiled-comment is TEST-only
  (`Recording` stub) — not a production hot path. `AbortableByteLink` uses a lock-free
  `Arc<AtomicBool>` (link.rs:70,90), one relaxed-cost `SeqCst` load per I/O — negligible.
- **Timers:** `POLL_INTERVAL = 20 ms` sleep-poll in `connect`/`answer`/`read`/`disconnect`
  loops (datalink.rs:131,474,640,805). T1 recovery sleeps a full `t1` between rounds
  (await_window/await_ack). These are bounded sleeps, NOT busy-waits — CPU idle between polls.

## Findings

No significant findings.

The link is correctly architected for a low-rate radio channel: bulk chunked reads
(512 B/syscall), single-write-per-frame TX, no lock held across blocking I/O, and
sleep-bounded (not busy-spin) poll/T1 timers. The 20 ms poll on a 1200-baud link is far
finer than byte arrival cadence and costs nothing measurable. The KISS decoder consumes
whole chunks per call (kiss.rs:59), so there is no syscall-per-byte or per-byte unbuffered
read anywhere in the real path. The one structural note below is sub-threshold for this
low-rate workload and is recorded for completeness only, not as an actionable finding.

### [MINOR] Per-frame `Vec` allocations on TX (sub-threshold, recorded only)

- **Location:** datalink.rs:151–155 (`send_frame` → `frame.encode()` + `kiss_data_frame`),
  kiss.rs:10 (`kiss_data_frame` allocates a fresh `Vec`), send_i:580 (`info.to_vec()` twice).
- **Problem:** Each transmitted frame allocates: `encode()` Vec, KISS-wrap Vec, and `send_i`
  clones `info` into both the frame and the `unacked` map. A reusable workhorse TX buffer
  (profile-pack memory lane) would eliminate these.
- **Impact:** LOW — at ≤7 in-flight frames over a 1200-baud link, frame cadence is tens of
  ms apart; allocator cost is invisible against airtime. Not on any contended path.
- **Confidence:** High (the allocations exist). **Effort:** Low. **Verification:** would need
  a TX-rate microbenchmark to show <1% — i.e. confirms it is not worth doing.
