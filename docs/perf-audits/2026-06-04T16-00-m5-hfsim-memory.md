# Perf Audit — Memory & Allocation — hf-channel-sim/src

Agent: glade-knoll-shoal. Dimension: memory/allocation only. READ-ONLY.
Scope: analysis.rs, channel.rs, fading.rs, lib.rs, noise.rs, params.rs, report.rs (excl. bin/).
Reachability: DEV/TEST-ONLY. Cost = sweep wall-time + peak memory on long signals; no latency deadline.
Frequency model: BER/SNR sweep = blocks × SNR points × trials; per-block work runs once per FADING_BLOCK_LEN (4096) samples consumed.

---

### [MAJOR] `generate_fading_block` re-allocates 3 full-block buffers per fading block, every block, for the whole sweep

Location: `fading.rs:42-46` (`complex_gaussian_block` → `Vec<(f32,f32)>` then `.map().collect()` into a 2nd `Vec<Complex<f32>>`), returns owned `Vec` at `:107`. Called from `channel.rs:96` / `:110` once per 4096 consumed samples, per tap (×2), per `process_block`.

Problem: each invocation allocates (a) the `(f32,f32)` pairs Vec inside `complex_gaussian_block` (rng.rs:37-42), (b) the mapped `Vec<Complex<f32>>` buf, then (c) the result is `extend`ed into the channel's `VecDeque` (channel.rs:103/113) — a 3rd copy into deque backing storage, after which buf is dropped. The pairs→Complex map is a pure re-layout that allocates a second full buffer when `Complex{re,im}` is layout-identical to `(f32,f32)`. Over a sweep, this is 2 taps × (signal_len/4096) blocks × SNR-points × trials allocations, each `block_len` complex elements.

Impact: per-block allocation churn scales with total sweep sample-volume. Dominant allocator pressure in the hot generation path. Reachability dev-only, but it is the sweep's inner loop.

Confidence: High (alloc sites are explicit).
Effort: Medium.

Verification plan: `dhat`/heaptrack alloc-count before/after on a representative sweep (e.g. 1e6 samples × 10 SNR pts). Fix candidates: (1) have `complex_gaussian_block` fill a caller-provided `&mut Vec<Complex<f32>>` (reused workhorse buffer, `clear()` per block) instead of returning; (2) drop the pairs intermediate by sampling directly into `Complex`. Correctness guard: existing `same_seed_same_block` / `block_is_unit_power` tests must still pass bit-identically.

### [MAJOR] Fading buffers are `VecDeque<Complex>` drained one element at a time via `pop_front` in the sample loop

Location: `channel.rs:41-42` (`tap1_buf`/`tap2_buf: VecDeque`), filled at `:103`/`:113`, drained `:115-116`; `out = Vec::with_capacity` at `:90`.

Problem: the per-sample loop (`for &s in input`, `:93`) does two `VecDeque::pop_front` per sample plus an `is_empty` check and conditional refill branch per sample. The fading block is a contiguous `Vec` that gets `extend`ed into a deque only to be popped one-at-a-time — the deque buys nothing over an index cursor into the contiguous block. The refill check runs per sample even though it can only fire every 4096 samples. Not a per-occurrence allocation problem (the deque backing is reused once grown), but it forces the extra `extend`-copy in the MAJOR above and adds branch/bookkeeping over the whole sample stream.

Impact: bounded; this is a frequency-× small-constant concern across the full sweep sample count, not an allocation-size concern. Listed MAJOR only because it is the structural reason the per-block buffer cannot be borrowed in place.

Confidence: High.
Effort: Medium (replace deque with `Vec` block + `usize` cursor; refill when cursor hits block_len).

Verification plan: bench branch/instruction count; `streaming_equals_one_shot` + `same_seed_bit_identical_output` must stay bit-identical.

### [MAJOR] `analysis::estimate_subcarrier_snr` builds a fresh `FftPlanner` per call + a `Vec` snapshot per window held for the whole run

Location: `analysis.rs:50` (`FftPlanner::new()` per call — no cache, unlike channel.rs:68 which caches), and `:69` `snap = vec![...; fft_size]` pushed to `snapshots` at `:85` for every window.

Problem: (1) Planner re-creation: each `run_characterization` (report.rs:91) calls this once, and a sweep calls `run_characterization` per (SNR-point × trial). The planner build (FFT algorithm selection/twiddle setup) is paid per sweep point rather than once. The prompt explicitly flags this as the no-cache site. (2) `snapshots: Vec<Vec<f32>>` retains `window_count × fft_size` f32 for the entire estimate and is then cloned wholesale into the report (report.rs serializes it). Per window this also allocates a fresh inner `Vec`. (3) `s_buf`/`y_buf` (`:63-64`) are `.to_vec()` clones of each window re-allocated per window — workhorse-buffer candidates.

Impact: planner-per-sweep-point is one-time-per-point waste multiplied by sweep breadth; the snapshots matrix is the peak-memory driver on long signals (grows linearly with window_count). Dev-only.

Confidence: High.
Effort: Medium. Planner: thread a cached planner/`Arc<dyn Fft>` in from the caller. snapshots: gate behind a flag if only `mean_snr_db` is needed downstream, or stream. s_buf/y_buf: reuse two buffers across windows with `clone_from`.

Verification plan: alloc-count + peak-RSS (heaptrack) before/after; `shape_matches_inputs`, `awgn_yields_expected_per_bin_snr` must pass.

### [MINOR] `report::run_characterization` clones the full channel output

Location: `report.rs:77` `let mut observed = channel_out.clone();`

Problem: a full `Vec<Complex>` clone of the entire signal so AWGN can be applied in-place while `channel_out` is kept for the analyzer. Unavoidable given both pre- and post-noise streams are needed, but it is one whole-signal allocation per sweep point. Noted for completeness; the clone is semantically required (analysis.rs needs both `clean`=channel_out and `observed`).

Impact: one signal-sized allocation per (SNR-point × trial). Bounded, justified.
Confidence: High. Effort: Low (leave as-is, or document; no cheaper option without restructuring add_noise to emit a separate noise vector).

Verification plan: none warranted; flagged as known-cost, not a defect.

### [MINOR] `complex_gaussian_block` and `noise::add_noise` allocate a per-call pairs `Vec`

Location: `rng.rs:37-42` (collect into `Vec<(f32,f32)>`); consumed by `noise.rs:60` (`let pairs = complex_gaussian_block(...)` then zipped at `:61`).

Problem: noise generation allocates a full `signal.len()` pairs Vec per `add_noise` call, immediately consumed by a zip and discarded. Returning `impl Iterator` (per the rust pack's "collect-then-iterate" anti-pattern, profile-pack lane `algorithmic`/`memory`) would let the noise loop sample lazily with zero intermediate allocation.

Impact: one signal-sized transient Vec per `add_noise` (= per SNR-point × trial). Dev-only.
Confidence: High. Effort: Low (make `complex_gaussian_block` return `impl Iterator<Item=(f32,f32)>`; `noise.rs:61` already zips it).

Verification plan: alloc-count before/after; `same_seed_same_noise`, `snr_0db_yields_equal_signal_and_noise_power` must pass (lazy iterator must draw RNG in the same order — guard with the existing determinism tests).

### [MINOR] `inv_sqrt2` recomputed; `bin_hz`/mask recomputed per block (hoistable, but bounded)

Location: `channel.rs:91` (`2.0f32.sqrt()` per `process_block` — trivial, hoist to const). `fading.rs:59-83` rebuilds the Gaussian frequency mask per block via a per-bin `.exp().sqrt()`. The mask depends only on (block_len, sample_rate, doppler) which are constant across the whole run — it could be precomputed once and reused, eliminating `block_len` transcendental calls per block. This is compute, not allocation, but the recompute touches `buf[i]` in place (no alloc), so it is noted as MINOR within scope (a cached mask Vec would be a one-time allocation replacing per-block recompute).

Impact: per-block transcendental recompute across the sweep. Bounded; borderline cold for this dimension.
Confidence: High. Effort: Low–Medium (cache mask in the channel struct).

Verification plan: bench; `zero_doppler_is_static`, `higher_doppler_decorrelates_faster` must pass.
