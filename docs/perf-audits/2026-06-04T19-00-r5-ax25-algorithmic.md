Dimension: algorithmic complexity & data structures ONLY
Scope: `src-tauri/src/winlink/ax25/{datalink.rs,frame.rs,kiss.rs,link.rs,params.rs,rfcomm.rs,mod.rs}`
Load profile: packet radio 1200/9600 baud (LOW). ARQ window ≤7 (mod-8). Per-frame O(frame_len) passes are acceptable; the watched concern is O(n²) over the window or a re-scan of all unacked per ack.

Calibration note: FCS/CRC is explicitly NOT computed here — the TNC owns FCS/flags/bit-stuffing (`mod.rs:3-4`, `frame.rs:1-2`). So the "FCS recompute" sub-lens has no surface. Address bit-packing, KISS escaping, and ARQ ack/retransmit handling are the only live surfaces.

### [MINOR] `pump_acks` retransmit path is O(window) per REJ/T1 round but `retransmit_from` does a per-N(S) BTreeMap point-lookup + clone

Location: `datalink.rs:557-571` (`retransmit_from`), called from `pump_acks:508` and `await_window:753` / `await_ack:720`.

Problem: `retransmit_from` walks `s = nr; while s != self.vs { unacked.get(&s).cloned(); ... }`, i.e. one `BTreeMap::get` (O(log w)) plus a full `Vec<u8>` payload `.clone()` per outstanding frame, each round. `ack_through` (`:539-551`) similarly loops `while s != nr { unacked.remove(&s) }`. These are O(w·log w) over the window per ack/REJ event, and the `.cloned()` re-allocates each retransmitted payload (up to paclen=128 bytes) every retransmit round.

Impact: LOW. w is clamped to ≤7 (`datalink.rs:659`, `params.rs:21`), and events fire at packet rate (T1 default 3 s). Aggregate cost is trivial. The payload clone is the only real allocation, and it is unavoidable given `send_frame` consumes an owned `Frame`. Not the "re-scan ALL unacked per ack" anti-pattern the brief flags — the walk is bounded by the live window, not by total traffic.

Confidence: High (code is explicit).
Effort: Contained (would need `send_frame` to accept `&[u8]` info to drop the clone; a data-structure change, not a hot-path concern at this scale).
Verification: window is `clamp(1,7)`; `criterion` on `retransmit_from` over a full 7-frame window would show sub-microsecond cost — not worth measuring.

### [MINOR] `recv_frame` filters every decoded frame against `mycall` by `String` field compare; foreign-frame fast path re-decodes

Location: `datalink.rs:166-205` (`recv_frame`), `pump_acks:491` peer check.

Problem: each inbound body is `Frame::decode`'d (full address-path parse, `String` allocs per callsign at `frame.rs:61-66`) then matched on `dest.call == mycall.call` (a `String` eq). On a shared RF channel, foreign frames are decoded in full before being discarded. The address decode allocates a `String::with_capacity(6)` + `trim_end().to_string()` (a second alloc) per address, per frame (`frame.rs:61,66`).

Impact: LOW. Decode is O(frame_len) per frame — exactly the acceptable per-frame pass the brief sanctions. At 1200 baud the channel delivers a few frames/sec; the two small per-address allocations are immaterial. Flagged only because it is the closest thing to a repeated-allocation pattern in scope; there is no quadratic here.

Confidence: High.
Effort: Localized (could compare against a pre-encoded 7-byte address to skip the String alloc, but the win is unmeasurable at packet rates).
Verification: n/a — below the noise floor for 1200/9600-baud traffic.

## Examined, no finding

- `frame.rs` `Address::encode`/`decode` (`:45-72`): fixed 6-byte loops, O(1). No per-bit loop — shifts whole bytes. Fine.
- `frame.rs` `Path::encode`/`decode` (`:218-258`): bounded to ≤4 addresses; `Vec::remove(0)` at `:255-256` is O(1)-amortized over a 2–4 element vec, not a concern. `Vec::with_capacity` already pre-sized at `:222`.
- `kiss.rs` `kiss_data_frame` / `KissDecoder::push` (`:10-23,59-91`): single O(body_len) escape/de-escape pass, no re-scan. `with_capacity(body.len()+4)` pre-sized. `out.extend_from_slice(&[FESC,..])` builds a 2-byte temp array (stack, no heap). Correct linear framing.
- `datalink.rs` `accept_inbound_i` (`:597-622`), `send_i` (`:574-585`): O(info_len) extend / single insert. No quadratic.
- `link.rs`, `rfcomm.rs`: plumbing + one-time SDP parse (`parse_spp_channel` is a single O(lines) pass over `sdptool` output at connect time, not hot). `hex_dump` is trace-only behind an env gate.

No `Vec::contains`/`.iter().any()` in a loop, no sort-per-iteration, no re-scan of total traffic per ack, no accidental quadratic anywhere in scope.
