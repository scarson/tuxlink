## Execution Cost Map

> Architectural awareness, NOT a to-do list. **NOTE: latent.** The crate
> has no in-tree caller today: `tuxmodem_phy` dependency is commented out and
> the live RX path uses hard-decision slicing that bypasses soft FEC entirely.
> Every region below is currently **dead from any runtime path**. Each becomes
> live *per received codeword* (encode) and *per codeword × up-to-`max_iters`
> SPA iterations* (decode) once FEC is wired into the PHY per-FEC-block path.
> `MAX_ITERS_OFDM = 50` (`codec.rs:35`) is the iteration cap that multiplies
> nearly all decode-side cost.

### Structural constants that drive the costs

- WiFi family (`codes/ofdm_wifi_family.rs`): n ∈ {648, 1296}, 24 column-blocks,
  target column weight ≈ 3 (`target_col_weight_per_blockcol = 3.0`, line 72).
  So edge count E ≈ 3·n ≈ **~1.9k edges (n=648)** to **~3.9k edges (n=1296)**.
  m = n−k rows; row weight grows with rate (fewer rows ⇒ denser rows at R5_6).
- Floor code (`codes/floor_rate14.rs`): n=2048, k=512, m=1536, regular (3,4):
  E = 3·n = 4·m = **6144 edges**, row weight exactly 4, col weight exactly 3.
  (Note: floor code currently `RankDeficient` ⇒ `Encoder::new` panics; encode
  path for the floor family is not yet functional — `decode.rs` still works on
  its H since the decoder needs no inverse.)

### Likely time-concentration regions

- **`Decoder::decode` SPA iteration loop — `decode.rs:158–227`** — basis: the
  outer `for iter in 0..max_iters` (≤50) wraps four full edge-sweeps per
  iteration (check update, variable update, posterior, convergence). This is
  FREQUENCY (every codeword) × HIGH UNIT COST (≤50× the per-iteration edge
  work). It is the unambiguous decode-path hot center. — confidence: **High** —
  overlaps the primary likely hot-spot.

- **Check-to-variable update — `decode.rs:162–188`** — basis: for each check
  `c`, an inner double loop computes `boxplus` over all `i2 != i` of `incoming`
  (`for i in 0..vars.len()` × `for (i2,..) in incoming`). That is **O(row_len²)
  boxplus calls per check**, i.e. Σ_c row_len_c² per iteration — *super-linear in
  row weight*, unlike the textbook forward/backward O(row_len) scan. At R5_6
  (dense rows) this term dominates the iteration. Each `boxplus` itself is two
  `tanh` + one `atanh` (`llr.rs:23–28`) — transcendental, ~tens of cycles each.
  So this is FREQUENCY (per check, per iter, per codeword) × the most expensive
  per-edge primitive in the crate. — confidence: **High** — overlaps a likely
  hot-spot; the O(row_len²)×transcendental combination is the single densest
  cost knot.

- **`boxplus` — `llr.rs:23–28`** — basis: cheap-looking leaf function, but
  called Σ_c row_len_c² × max_iters times per codeword (see above). Two
  `tanh` + `atanh` per call. Cheap-function × extreme-frequency = a top
  aggregate consumer. Phase-8 note in the source already flags swapping for the
  min-sum approximation. — confidence: **High** — overlaps a likely hot-spot.

- **Variable-to-check update — `decode.rs:191–204`** — basis: per variable,
  builds an `incoming` Vec then O(deg) updates; total **O(E) per iteration**,
  linear, only adds/subtracts. Plus a per-variable heap `Vec` allocation for
  `incoming` every iteration. Linear and arithmetic-cheap relative to the
  check update, but the repeated small-Vec allocation is a steady allocator
  load (E-edge-worth of transient Vecs × 50 iters). — confidence: **High** —
  map-only (second-order vs. check update, but the per-iter allocation churn is
  worth noting).

- **Posterior + hard decision — `decode.rs:207–216`** — basis: per variable,
  re-reads all adjacent `msg_c_to_v` via `c_edge_pos` and sums; **O(E) per
  iteration**, runs every iteration (not just at convergence). Re-walks the same
  edges the variable update just walked. Linear, arithmetic-cheap. — confidence:
  **High** — map-only.

- **Convergence check — `decode.rs:219–222`** — basis: per iteration, XOR-folds
  every check row over `decoded` until first failure: **O(E) worst case per
  iteration** (short-circuits on first unsatisfied check, so typically cheap
  early, full-cost only near convergence). — confidence: **High** — map-only.

- **`Decoder::decode` per-call setup — `decode.rs:137–156`** — basis: clones
  `channel` (Vec<f32> len n) and allocates the full nested `msg_v_to_c` /
  `msg_c_to_v` edge-message structures (E f32 each, as Vec<Vec<f32>>) once per
  decode. One-time per codeword, dwarfed by the 50× iteration body, but it is a
  non-trivial per-codeword allocation of E·2 floats in a pointer-chasing
  Vec<Vec<_>> layout. — confidence: **Med** — map-only (amortized away by the
  iteration loop; flagged for the cache-layout note below).

- **`Encoder::try_new` Gaussian elimination — `encode.rs:74–126`** — basis:
  O(m²·words_per_row) = O(m²·n/64) word-XORs for RREF over the packed dense
  matrix (`for col in k..n` × `for r in 0..m` × `for w in 0..words_per_row`).
  The source comment quantifies it: floor code (m=1536, n=2048) ≈ 5 s packed
  (~150 s unpacked). **HIGH unit cost but construction-time only** — runs once
  per codec in `OfdmAdaptiveCodec::new`, not per codeword. The amplifier is
  `ofdm_wifi_family::build` calling `try_new` up to `MAX_SEED_ITERATIONS = 64`
  times searching for a rank-full H (`codes/ofdm_wifi_family.rs:37–47`), so
  codec construction can pay this elimination many times over. — confidence:
  **High** — map-only (cold path: one-time codec init, never per-block).

- **`Decoder::new` Tanner-graph adjacency build — `decode.rs:59–109`** — basis:
  builds `var_to_checks`, `check_to_vars`, and the two edge-inverse maps. The
  inverse-map construction uses `.iter().position(...)` (linear scan) per edge
  ⇒ roughly O(E · max_degree). One-time per codec (cold). Modest vs. the
  encoder's Gaussian elimination. — confidence: **High** — map-only (cold).

- **Matrix construction `ofdm_wifi_family::build_with_seed` — lines 49–124** —
  basis: ChaCha8 RNG draws over m_blocks×n_blocks, then expands each non-zero
  block into Z per-row pushes, then `sort_unstable` + `dedup` per row. O(E) plus
  RNG. Re-run up to 64× by the seed search. Cold (codec init). — confidence:
  **High** — map-only.

- **`floor_rate14::build_with_seed` — lines 42–81** — basis: builds 6144 stubs,
  `shuffle`s them, partitions into 1536 rows of 4, up to 32 reshuffle attempts
  on duplicate collisions. O(E) per attempt + shuffle. Cold (codec init).
  Currently feeds a code whose encoder panics. — confidence: **High** —
  map-only.

- **Interleave / deinterleave-perm — `interleaver.rs:30–48`, `codec.rs:192–204`**
  — basis: O(n) bit moves through a `BitVec` matrix on encode; on decode,
  `deinterleave_index_perm` builds an O(n) permutation then gathers n LLRs.
  Linear, per-codeword, but a single n-pass — negligible beside one SPA
  iteration, let alone 50. The encode path also does **two** redundant LLR-sign
  passes in `decode_soft` (`codec.rs:146` builds `llr_bitvec_signs` then
  discards it at line 151 with `let _ =`) — dead O(n) work, not hot, worth
  noting as a trivially removable pass. — confidence: **High** — map-only.

- **CRC-32 `append_crc32` / `verify_crc32` — `crc.rs:44–73`** — basis: packs n/8
  bytes (`bits_to_bytes`, bit-at-a-time loop) then one `crc` crate checksum over
  ~k/8 bytes. O(k) per codeword, table-driven CRC. Per-codeword but linear and
  small (k ≤ 972 bits ⇒ ~120 bytes). — confidence: **High** — map-only.

- **`codec.rs` bit↔byte marshalling — `bytes_to_bitvec` / `bitvec_to_bytes`,
  lines 97–103** — basis: the FecCodec contract is one-bit-per-byte, so every
  encode/decode does O(n) bit-by-bit conversions at the crate boundary. Linear,
  per-codeword, cheap individually but on every call. — confidence: **High** —
  map-only.

- **`puncture.rs` / `stats.rs`** — basis: puncture is an empty v0.6 stub (no
  code); stats is a plain data struct. Zero runtime cost. — confidence: **High**
  — map-only (no-ops).

### Notes for architecture

- **Decode dominates; encode is cheap-per-block but pays a one-time elimination.**
  Per-codeword, ~99% of work is the 50-iteration SPA loop. Encode-per-block is
  O(parity_eqs) XORs (`encode.rs:164–167`) — linear, cheap. The encoder's
  expensive part (Gaussian elimination, possibly ×64 seeds) is amortized into
  codec construction and never touches the per-block path.

- **The check update is the asymptotic risk.** `decode.rs:171–187` is
  O(row_len²) per check, not the textbook O(row_len) forward/backward scan. For
  high-rate codes (R5_6, denser rows) and the floor code (row weight 4 is small,
  so fine there) this quadratic-in-row-weight term is the thing that grows. If a
  future profiling pass finds decode latency over budget, the two levers the
  source itself flags are (a) min-sum / sign-min `boxplus` approximation
  (`llr.rs:21`) and (b) forward/backward check-node recursion to kill the O(²).

- **Allocation churn inside the iteration loop.** Both the check update
  (`incoming`, line 165) and variable update (`incoming`, line 193) heap-allocate
  a fresh `Vec` per node per iteration ⇒ O(n · max_iters) transient
  allocations per codeword. The edge-message store is `Vec<Vec<f32>>`
  (pointer-chasing, poor cache locality). A flat CSR-style edge array + scratch
  reuse across iterations would remove the churn and improve locality — relevant
  only once this is on a live, throughput-sensitive path.

- **Early termination is the real-world cost saver.** The `break` at
  `decode.rs:225` exits as soon as all parity checks pass, so at usable SNR the
  effective iteration count is far below 50. Worst-case (non-converging /
  heavily-corrupted blocks, e.g. the `corrupted_codeword` test) pays the full
  50× — that is the latency budget to size against.

- **No I/O, no concurrency, single-threaded** — all cost is CPU/ALU + allocator.
  The HF per-codeword cadence is slow (low symbol rate), so even the full 50×
  SPA budget is likely comfortably within real-time once integrated; this map is
  about *where* the cycles sit, not a claim that any of it is currently too slow.

- **Reachability caveat restated:** nothing here is exercised at runtime today
  (no PHY caller; RX bypasses soft FEC). Treat all "hot" labels as *would-be-hot
  once FEC is wired in*, not as observed live cost.
