### [MINOR] `send_i` clones the info payload twice per outbound I-frame

**Location:** `datalink.rs:574-585` (`send_i`).

**Problem:** `send_i(info: &[u8])` allocates `info.to_vec()` once to build the transient `Frame` (line 580), then a *second* `info.to_vec()` to store in `unacked` (line 582). The Frame is immediately consumed by `send_frame` → `encode` (which `extend_from_slice`s the info into yet another `Vec`) and dropped. So one logical payload incurs two `Vec` allocations + the encode buffer, when one retained copy in `unacked` would suffice: the frame could borrow the stored slice. Restructuring to insert into `unacked` first, then build the `Frame` borrowing `&unacked[&ns]` (or factoring an encode-from-parts path that takes `&[u8]`), removes one alloc per sent frame.

**Impact:** LOW. One avoidable `Vec` (≤128 B) per I-frame; at 1200 baud the send rate is single-digit frames/sec, so this is ~hundreds of bytes/sec of churn, not a bottleneck. Flagged because it is the exact "clone of frame buffer in the ARQ path" the dimension names and is cleanly removable.

**Confidence:** High (the double `to_vec` is explicit). **Effort:** Medium (touches the Frame/encode boundary). **Verification:** `cargo build`; existing `write_tests` / `recovery_tests` cover send + retransmit; optionally a `dhat` alloc-count diff on `write_under_paclen_sends_one_i_frame`.

### [MINOR] Inbound I-frame info is allocated into a `Vec` then immediately copied out and discarded

**Location:** `frame.rs:341` (`info = bytes[off + 2..].to_vec()`) → consumed at `datalink.rs:602` (`self.inbound.extend(info.iter().copied())`).

**Problem:** `Frame::decode` always allocates `info` as an owned `Vec<u8>`. On the inbound data path that `Vec` exists only to be copied byte-by-byte into the `inbound: VecDeque<u8>` (line 602) and then dropped when the `Frame` falls out of scope. The decode-time allocation is pure intermediate churn: the bytes already live in the decoder's de-escaped `body` buffer. A decode variant that returns the info as a borrowed `&[u8]` into `body` (or `accept_inbound_i` reading the slice directly) would let `inbound.extend` copy straight from the source with no intermediate `Vec`.

**Impact:** LOW. One avoidable `Vec` (≤128 B) per *received* I-frame, at RF receive rate. Correctness-neutral. Flagged as a clearly-avoidable intermediate-Vec-built-then-discarded per the dimension brief.

**Confidence:** High. **Effort:** Medium (decode returns owned today; a borrowed accessor or a `decode_into` is an API change). **Verification:** `read_tests::read_delivers_in_order_i_frames_and_replies_rr` already pins behaviour; `cargo test`.

### Notes (examined, NOT flagged — calibration)

- **`retransmit_from` `.get(&s).cloned()`** (`datalink.rs:560`): clones the unacked buffer to build a transient retransmit Frame. This IS a frame-buffer clone in the ARQ path, but it fires only on REJ / T1 recovery (the error path, rare) and the window is ≤7 — not worth the borrow-checker fight to elide. Correctly left.
- **`unacked: BTreeMap`** is hard-bounded: `write` clamps `maxframe` to ≤7 (`datalink.rs:659`) and `send_i` blocks via `await_window` before exceeding it. **No unbounded retransmit-queue growth** — the dimension's headline concern is absent by construction.
- **`kiss_data_frame`** (`kiss.rs:10`) and **`Path::encode`** (`frame.rs:222`) both pre-size with `Vec::with_capacity`. The KISS escape pass can under-size when escapes occur, but escapes are rare and the body is tiny; not worth flagging. Good as-is.
- **`pending_frames` / `inbound` VecDeques**: drained as consumed; bounded by what one 512-B link read decodes. No leak.
- **`rfcomm::hex_dump` `format!` per byte** (`rfcomm.rs:200`): allocates a `String` per byte + a `Vec`, but it is gated behind the `TUXLINK_RFCOMM_TRACE` env var (opt-in diagnostic, off in production). Not a production-path cost.
- **`connect`/`answer` per-call `.clone()` of `Address`/`digis`/`params`**: once per session setup, not per frame. Negligible.
