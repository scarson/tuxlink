# ARDOP modem — memory & allocation audit (m3)

Agent: glade-knoll-shoal. Dimension: memory/allocation only. READ-ONLY audit.
Scope: `src-tauri/src/winlink/modem/ardop/{data,frame,b2f,command,session,transport}.rs`.
Load calibration: ARQ at low HF rates (hundreds bps–few kbps); status poll a few/sec.
At these rates per-frame allocation *frequency* is modest — only clearly-avoidable,
multiply-redundant copies are flagged.

---

### [MINOR] Inbound ARQ payload is copied three times before the B2F engine sees it

Location: `frame.rs:90` (`self.buf[5..total].to_vec()`), `data.rs:145`
(`self.leftover.extend(frame.payload)`), `data.rs:104-110` (`drain_leftover`).

Problem: Each inbound ARQ frame's payload makes three trips through memory on a
path that needs zero owned intermediates:
1. `frame.rs:90` allocates a fresh `Vec<u8>` per frame (`to_vec()`) for `DataFrame.payload`.
2. `data.rs:145` copies that `Vec` into the `leftover: VecDeque<u8>` via `extend`
   (whole-body copy; the just-allocated `Vec` is then dropped).
3. `drain_leftover` (`data.rs:104-110`) copies out of the `VecDeque` byte-by-byte
   in a `zip` loop into the caller's `buf`.
The decoder already holds the bytes contiguously in `DataDecoder.buf`; the payload
could be handed to the `Read` consumer with at most one copy (decoder buffer →
caller `buf`), keeping a cursor/offset instead of a `VecDeque<u8>`.

Impact: low-HF-calibrated — at hundreds bps–few kbps the per-frame rate is low, so
this is not a throughput limiter. It is a clearly-avoidable 3x-copy of every session
byte and a `VecDeque<u8>` (per-element, not bulk, drain) where a `Vec<u8>` + read
cursor — or returning a slice from the decoder — would do one bulk `copy_from_slice`.
Mainly a cleanliness/allocation-discipline win, not a measured hotspot.

Confidence: HIGH (code is explicit). Effort: MEDIUM (reshape `leftover` to
`Vec<u8>` + consumed-offset, or expose a borrowing `next_frame_into`/slice API on
`DataDecoder`; keep the `arq_up` drop gate and `bytes_rx` accounting intact).

Verification: `dhat`/heaptrack on a release build replaying a recorded ARQ session
through `DataSocket::read`; count allocations attributable to `frame.rs:90` and bytes
moved through `leftover`. Expect ~1 alloc + 1 bulk copy per frame after the change vs
1 alloc + 2 copies now.

### [MINOR] `DataDecoder.buf` drains from the front per frame (O(remaining) memmove)

Location: `frame.rs:91` (`self.buf.drain(..total)`), also `frame.rs:74`
(`self.buf.drain(..2)` resync path).

Problem: `Vec::drain(..total)` removes from the front, which memmoves every
*remaining* buffered byte left by `total` on each frame extraction. When one socket
`read` delivers several back-to-back frames (`data.rs:266` pushes one chunk, then
`pump_decoder` pulls all frames in a loop), the tail is shifted once per frame —
O(frames × remaining) within a chunk. A read-cursor (advance an offset, compact only
when the offset grows large) would make extraction O(1) amortized.

Impact: low-HF-calibrated — chunk sizes at these rates are small (the read buffer is
4 KiB, `data.rs:258`) and frames-per-chunk is low, so the absolute memmove volume is
small. Flagged because it's the textbook "drain-from-front in a parse loop" pattern,
not because it's a measured bottleneck here.

Confidence: HIGH. Effort: MEDIUM (introduce a `start` offset; compact in `push` or
when `start` exceeds a threshold; the malformed-resync `drain(..2)` becomes
`start += 2`).

Verification: micro-benchmark `DataDecoder` (criterion, release) feeding a multi-frame
chunk; compare ns/frame and bytes-moved (instrument or reason from `total`) between
drain-from-front and cursor variants.

### [MINOR] Per-line `String` allocation in the cmd reader thread

Location: `session.rs:90-91` (the file containing `CmdSocket`; `s.to_owned()` into a
fresh `String` per line), then `Command::parse(&line)` re-`trim`s.

Problem: The cmd reader correctly reuses `buf: Vec<u8>` with `buf.clear()` each
iteration (`session.rs:78,80`) — good. But it then `to_owned()`s the UTF-8 view into a
new `String` per line solely to pass `&str` to `Command::parse`, which immediately
`trim`s and re-tokenizes (`command.rs:88-95`). `Command::parse` could take the
`&str` borrowed directly from `std::str::from_utf8(&buf)` with no owned `String`.

Impact: negligible at the realistic rate (cmd messages a few/sec: NEWSTATE, BUFFER,
CONNECTED). Recorded for completeness; not worth prioritizing.

Confidence: HIGH. Effort: LOW (pass the borrowed `&str` from `from_utf8` straight into
`Command::parse`; the empty/UTF-8 guards stay). Verification: it's a borrow vs owned
swap — confirm by `cargo build` + existing cmd-parse tests; no behavior change.

## What was examined and found clean

- `b2f.rs`: wraps the data stream in one `BufReader`; no per-frame allocation of its
  own. `Arc::clone` at `b2f.rs:105` is a refcount bump, not an allocation. Clean.
- `transport.rs` status path: `throughput_samples: VecDeque` is bounded — pruned to
  `THROUGHPUT_WINDOW` on every append (`transport.rs:348-355`) AND on every read
  (`current_throughput_bps`, `transport.rs:389-396`), so it cannot grow unbounded
  across a session. `bytes_tx`/`bytes_rx` are `u64` counters, not buffers.
  `populate_derived_meters` (`transport.rs:303-316`) does no per-tick clone of
  accumulated buffers. Clean.
- `data.rs` write path (`data.rs:324-329`): one `Vec::with_capacity(2 + n)` per
  `write` framing the outbound payload — correctly pre-sized; not flagged.
- `drain_pending` scratch buffer (`data.rs:202`) is a stack `[0u8; 8192]`, reused
  across the drain loop; no per-iteration heap alloc. Clean.
