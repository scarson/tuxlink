# Performance Audit — `tuxmodem-fec` — Dimension: Memory & Allocation

**Auditor:** glade-knoll-shoal (memory/allocation lane only)
**Date:** 2026-06-04T15:00
**Scope:** `tuxmodem/crates/tuxmodem-fec/src/*.rs` (excl. `bin/`)
**Lens prior:** `performance-audit/profile-packs/rust.md` — Memory & allocation lane + Runtime/build notes.

## Reachability calibration

This crate is **LATENT**. No in-tree callers: `codec.rs` depends on `tuxmodem_phy::coded_modulation::FecCodec`, the PHY dep is commented out, and the live receive path uses hard-decision slicing that bypasses FEC entirely. Reachability today is **zero**. The findings below are ranked against the cost the code **will** have once FEC is wired into the per-FEC-block receive path:

- `Decoder::new` / `OfdmAdaptiveCodec::new`: **per-codec construction**, once per `(block_n, rate)` codec object, amortized across all frames. One-time cost.
- `Decoder::decode` / `decode_soft`: **per-received-codeword** (per FEC block / per frame, NOT per OFDM symbol). Each call runs up to `MAX_ITERS_OFDM = 50` SPA iterations (`codec.rs:35`), early-terminating on convergence.
- Per-iteration bodies in `decode`: **per-codeword × per-iteration** — the innermost cost multiplier. Up to 50× per frame.

Block sizes that set the allocation magnitude: n ∈ {648, 1296} (OfdmAdaptive), k = n·rate. Edge count E = sum of row lengths; column weight ≈3, so E ≈ 3n per the construction (`ofdm_wifi_family.rs:72`). Node counts: n variables + (n−k) checks.

All findings fire **once FEC is wired in**; today they are dormant.

### [MAJOR] Per-iteration `incoming` Vec allocated for every check and every variable node inside the SPA loop

**Location:** `decode.rs:165-169` (check-to-variable update) and `decode.rs:193-197` (variable-to-check update).

**Problem:** Inside the `for iter in 0..max_iters` loop, both message-passing half-iterations allocate a fresh `Vec<f32>` scratch buffer for *every node* on *every iteration*:

```rust
// check-to-variable, per check c:
let incoming: Vec<f32> = vars.iter().enumerate()
    .map(|(i, &v)| msg_v_to_c[v][self.v_edge_pos[c][i]]).collect();   // :165
// variable-to-check, per variable v:
let incoming: Vec<f32> = checks.iter().enumerate()
    .map(|(j, &c)| msg_c_to_v[c][self.c_edge_pos[v][j]]).collect();    // :193
```

The check loop runs over all `(n−k)` checks; the variable loop over all `n` variables. Each `collect()` is a heap allocation (and matching free at scope end). So per `decode` call the allocation count is:

`iters × ( (n−k) + n )` heap allocs from these two sites alone.

Worst case for N1296 (n=1296, n−k up to 648 at rate 1/2) at the full 50 iters: ≈ 50 × (648 + 1296) ≈ **97,000 short-lived Vec alloc/free pairs per decoded frame**, each of length = node degree (≈ check degree 6–7 for the check side, column weight ≈3 for the variable side). The buffers are tiny and uniform in size per node, making them ideal "workhorse buffer" candidates: the lens calls out exactly this — "Loop-body allocations that could be 'workhorse' buffers: declare the collection outside the loop, `clear()` inside — preserves capacity and eliminates per-iteration allocation."

These `incoming` Vecs are pure scratch — read once to compute the outgoing messages, never retained. They can be hoisted to a single reusable buffer declared before the `for iter` loop, `clear()`ed (or overwritten) per node. Because node degree varies, a single buffer sized to `max_degree` that is reused for both the check and variable passes eliminates essentially all per-iteration allocation in the SPA loop.

Note also `decode.rs:207-214` (posterior pass): it sums via `.map(...).sum()` without collecting, so no allocation there — good — but it recomputes the same per-variable incoming-message sum already available from the variable-update pass; that's a compute redundancy, not an allocation one, so out of this lane's scope beyond noting it.

**Impact:** Per-frame allocation churn scaling as `iters × node_count`. On the embedded HF-modem target (Pi-class), high-frequency short-lived allocation pressures the allocator and the cache; this is the dominant allocation cost in the decode hot path once wired. Latency: contributes to per-frame decode latency proportional to iteration count — and iteration count is highest exactly on the noisy frames that don't early-terminate, i.e. worst-case latency aligns with worst-case allocation. **Confidence:** Strong-static (allocation sites are unambiguous `collect()` into owned `Vec` inside the iteration loop; magnitude derived from code structure + documented n/edge sizing).

**Effort:** Contained (+low). Hoist two buffers above the `for iter` loop; reuse via `clear()`/index-overwrite. The edge-position maps (`v_edge_pos`, `c_edge_pos`) already give O(1) gather, so the rewrite is mechanical. Risk: must preserve the read-all-then-write semantics (the buffer is fully populated before any outgoing message is written, so in-place reuse is safe — no aliasing hazard).

**Verification plan:** Allocation-count proof. Add a `criterion` bench `decode_n1296_r12_50iter` on a `--release` build with a fixed non-converging LLR vector (forces all 50 iters), instrument with `dhat` (already an idiomatic Rust alloc profiler per the lens) before/after. Expected: allocs/op drops from ≈`iters×(2n−k)` to a small constant (the once-per-call message arrays + channel copy). Correctness guard: existing `decode_zero_noise_returns_input` and `decode_one_bit_flip_recovers` tests plus `codec.rs` round-trip tests must still pass bit-identically — message values are unchanged, only the buffer's storage lifetime changes.

### [MINOR] `decode_soft` rebuilds the deinterleave index permutation on every call instead of caching it

**Location:** `codec.rs:149` calling `deinterleave_index_perm(self.n, INTERLEAVER_ROWS)` (`codec.rs:192-204`).

**Problem:** `deinterleave_index_perm` allocates and fills a `Vec<usize>` of length `n` (`codec.rs:195`) and is recomputed on every `decode_soft` call. Its inputs `self.n` and `INTERLEAVER_ROWS` are both **constant for the lifetime of the codec** — the permutation never changes between frames. The codec doc-comment even advertises the design intent: "Constructs the parity-check matrix + encoder + decoder once at codec-construction time; per-encode and per-decode are then pure data-plane work" (`codec.rs:38-40`). This permutation violates that intent — it's invariant structure rebuilt per call.

The lens flags this directly: "Repeated computation inside a loop that could be hoisted: re-parsing strings, re-compiling regexes, re-constructing maps or sets that are invariant over iterations" and "Work done at runtime that could be `const`-evaluated or pre-computed."

It should be computed once in `OfdmAdaptiveCodec::new` and stored as a `Vec<usize>` (or `Box<[usize]>`) field, then indexed in `decode_soft`.

Secondary, same site: `codec.rs:146` builds `llr_bitvec_signs: BitVec<u8>` of length n and then immediately discards it (`let _ = llr_bitvec_signs;` at `:151`, commented "sanity-check witness; could remove"). This is a per-call allocation of an n-bit `BitVec` plus the n-element iterator pipeline that feeds it, whose only consumer is `let _ =`. It is **pure dead allocation** on the decode path and should be deleted.

**Impact:** Two per-frame allocations (one `Vec<usize>` of length n = up to 1296 × 8 bytes ≈ 10 KB; one discarded n-bit `BitVec`) plus the fill loops. Small relative to the SPA loop, but it's per-codeword overhead that is trivially removable and contradicts the codec's stated "build once" contract. Latency: negligible next to 50 SPA iterations, but non-zero and on the critical path. **Confidence:** Strong-static (the perm inputs are provably call-invariant; the `BitVec` is provably dead).

**Effort:** Localized (+low). Add a `deint_perm: Vec<usize>` field, populate in `new`, index in `decode_soft`; delete the dead `llr_bitvec_signs` block (`:146`, `:151`).

**Verification plan:** Correctness guard via existing `round_trip_*` tests in `codec.rs` (the permutation values are identical, only their computation site moves; deleting `llr_bitvec_signs` removes an unused binding). Allocation argument: `dhat`/alloc-count on `decode_soft` drops by 2 allocs/call; no behavioral change.

### [MINOR] SPA message state stored as jagged `Vec<Vec<f32>>`, one heap allocation per node, reallocated per `decode` call

**Location:** `decode.rs:142-152` (`msg_v_to_c`, `msg_c_to_v`); structurally mirrored in the cached adjacency `decode.rs:41-53`.

**Problem:** The two per-edge message arrays are built fresh on every `decode` call as `Vec<Vec<f32>>`:

```rust
let mut msg_v_to_c: Vec<Vec<f32>> = self.var_to_checks.iter()
    .map(|(v, checks)| vec![channel[v]; checks.len()]).collect();   // :142
let mut msg_c_to_v: Vec<Vec<f32>> = self.check_to_vars.iter()
    .map(|vars| vec![0.0_f32; vars.len()]).collect();                // :148
```

Two issues stack here:

1. **Per-call reallocation of all node buffers.** These are allocated once per `decode` (not per iteration — correctly outside the `for iter` loop), so this is far less severe than the MAJOR finding. But it's still `n + (n−k)` inner-Vec allocations + 2 outer-Vec allocations on every frame. Since the `Decoder` is `&self` and decode is single-threaded sequential per the stack brief, these buffers could be owned scratch reused across calls (would require `&mut self` or interior `RefCell`/`Cell`-backed scratch — a design change, hence ranked MINOR not MAJOR).

2. **Jagged layout pays an allocation + a pointer-chase per node.** `Vec<Vec<f32>>` is the lens's "needless indirection" shape: each inner `Vec` is a separate heap region (8-byte length + 8-byte cap + 8-byte ptr = 24-byte header each, plus the payload), and gather/scatter through `msg_v_to_c[v][pos]` is a double indirection. A **flat CSR-style layout** — one `Vec<f32>` of length E (edge count) plus per-node start offsets (already derivable from the cached adjacency) — collapses `n + (n−k)` allocations to a single one, improves locality (messages for a node are contiguous), and shrinks the struct. The same flattening applies to the four cached jagged maps in the `Decoder` struct (`var_to_checks`, `check_to_vars`, `v_edge_pos`, `c_edge_pos`, `decode.rs:41-53`) — those are built once in `new` (one-time cost, lower priority) but the flat form would also speed the per-iteration gathers that index them.

**Impact:** Per-frame: `n + (n−k) + 2` allocations for message state (≈1944 allocs/frame for N1296 r1/2) plus pointer-chase overhead on every message access inside all 50 iterations. The per-access indirection is the part that compounds with iteration count. Latency: contributes to steady-state per-frame decode latency; the flat layout's locality win is hard to quantify statically but real on cache-bound embedded targets. **Confidence:** Heuristic for the locality/indirection win (needs measurement to size); Strong-static for the allocation count.

**Effort:** Cross-cutting (+low) — flattening to CSR touches the `Decoder` struct fields, `new`, and the four index sites in `decode`; the message arrays flatten naturally alongside. Mechanical but spans the file. Reusing scratch across calls additionally requires an ownership-model decision (`&mut self` vs interior mutability).

**Verification plan:** `criterion` decode bench + `dhat` alloc-count before/after, `--release`. Expect allocs/frame to drop from ≈`2(n)+2` to O(1). Correctness guard: all `decode.rs` and `codec.rs` round-trip tests bit-identical. The CSR offsets must be validated equal to the current jagged indexing (assert per-node slice boundaries match `var_to_checks[v].len()` etc. in a debug test).

## Out-of-lane observations (noted, not findings)

- `codec.rs:135-139,159` use `format!` to build `FecError::DecodeFailure` strings — `format!` allocates, but only on the **error path** (length mismatch / CRC fail), not the steady-state success path, so it is not a hot-path allocation. Correctly out of scope.
- `encode.rs:80,114-123` (`dense: Vec<Vec<u64>>`, `parity_eqs`) and `ofdm_wifi_family.rs:75,103` (`block_shifts`, `rows`) allocate substantial jagged structures, but exclusively in **construction** (`try_new`/`build`), which is one-time per codec and amortized to zero per frame. The encoder doc-comment already justifies the `Vec<u64>` packing as a deliberate construction-time speedup. Not a per-frame concern.
- `interleaver.rs` / `encode.rs::encode` allocate `BitVec`s per call but sit on the **transmit** path, not the SPA decode hot loop; the prompt's dimension centers the decode/SPA allocation, and these are bounded single-pass allocations of length n. Noted, low priority.
- `decode.rs:137` `channel: Vec<f32> = llrs.to_vec()` — one per-call copy of the input LLRs. Necessary if the decoder mutates/owns it, but it never mutates `channel`; it only reads `channel[v]`. A borrowed `&[f32]` would suffice, saving one length-n allocation+copy per frame. Borderline lane-relevant but small (one alloc vs the loop's thousands); folded here rather than as a standalone finding. Cheap to fix: take `llrs` by reference throughout instead of copying.

None. (No correctness defects observed in the memory/allocation review.
